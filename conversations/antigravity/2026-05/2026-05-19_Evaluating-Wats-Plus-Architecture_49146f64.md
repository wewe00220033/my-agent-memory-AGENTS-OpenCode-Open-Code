تخيل إن المشروع بتاعك ده عبارة عن "ورشة" فيها اتنين صنايعية:
1. **الصنايعي الأول (WebSockets):** ده واد خفيف وسريع جداً، بيعرف يفلتر الأرقام في ثواني.

### ❌ إيه كانت المشكلة في الكود القديم؟ (الوضع قبل التعديل)

1. **المدير كان طيب بزيادة (وهم التوازي):**
   كود الماستر بتاعك كان بيشغل "الصنايعي السريع" (WebSockets) ويقعد **يستناه** لحد ما يخلص شغله كله.. وبعدييييين يقوم مشغل "الصنايعي البطيء" (ADB). يعني هما مكنوش بيشتغلوا مع بعض أصلاً! كانوا بيشتغلوا "طابور بالدور"، وده بيضيع وقت طويل جداً في الـ Mass Checking.

2. **الدفتر بباب واحد (Database is locked):**
   لو حصل صدفة إن الصنايعية الاتنين حبوا يسجلوا رقمين مختلفين في الدفتر (الداتا بيز) في نفس الفيمتو ثانية، الدفتر كان بيقفل بابه ويضرب إيرور أحمر في وشك اسمه `Database is locked`، والداتا دي تضيع لأن الداتا بيز العادية مبتقبلش اتنين يكتبوا في نفس اللحظة.

---

### ✅ إيه اللي عملناه عشان نخليه وحش كاسر؟ (الوضع دلوقتي)

**1️⃣ تظبيط الدفتر (تفعيل الـ WAL Mode):**
دخلت على كود الداتا بيز وفعلت خاصية اسمها `WAL Mode`. دي عملت إيه؟ دي خلت الدفتر يشتغل بنظام "المسودة السريعة". بقى ممكن الصنايعي الأول يكتب في صفحة، والصنايعي التاني يكتب في صفحة تانية في **نفس اللحظة** من غير ما حد يعطل التاني ولا الداتا بيز تقع. وكمان زودت `timeout` عشان لو حصل زحمة، يستنوا بعض ثواني بدل ما يضربوا إيرور.

**2️⃣ المايسترو الحقيقي (تفعيل ThreadPoolExecutor):**
دخلت على كود المدير (الماستـر) وشلت طريقة "الطابور"، وحطيت مكانها أداة بتشتغل بالتوازي الحقيقي اسمها `ThreadPoolExecutor`. دي خلت المدير يدي الأمر للصنايعيين الاتنين ويقولهم: *"يالا أنتو الاتنين انطلقوا في نفس اللحظة!"*.
دلوقتي، أول ما بتشغل الماستر، الـ WebSockets بيطير يفلتر الأرقام ويرمي في الدفتر، وفي نفس اللحظة الـ ADB شغال بيجرب ويرمي في الدفتر.

## إيه اللي فيه صح؟
الجزء الصحيح هو إن:

UI Automator أصلًا يعمل عبر طبقة الـ accessibility ويرسل actions للنظام، وليس بالضرورة نفس مسار إدخال المستخدم الحقيقي في كل التطبيقات. [Source](https://getautonoma.com/blog/android-ui-automator-testing-guide)

## إيه اللي غلط؟
### 1) عبارة: `set_text()` “بيكتب الرقم كأنه صورة”
دي **غلط تقنيًا**.
هو لا يكتب “صورة”، بل يغير النص عبر آلية أتمتة/إمكانية وصول، لكن **ليس بالضرورة** بنفس سلسلة الأحداث التي تحدث مع إدخال المستخدم الحقيقي. فالمشكلة ليست “صورة”، بل غالبًا **اختلاف في مسار الإدخال والأحداث المصاحبة**. [Source](https://getautonoma.com/blog/android-ui-automator-testing-guide)

### 2) عبارة: “NEXT بيسأل هل المستخدم داس على الكيبورد؟ والـ buffer فاضي”
دي **مجرد فرضية**، وليست حقيقة مثبتة من اللوج المعروض.
الذي نعرفه فقط هو:
- النص ظهر/اتكتب
- الضغط على `NEXT` لم يغيّر الشاشة
لكن **لا نعرف يقينًا** السبب الداخلي: هل هو `TextWatcher`؟ هل هو `focus`؟ هل هو `onEditorAction`؟ هل هو custom widget؟ هل الزر disabled منطقيًا رغم ظهوره؟
إذن هذا **تفسير محتمل** وليس **دليل قاطع**.

### 3) عبارة: “الحل الوحيد 100% هو Macro”
دي **غلط**.
LDPlayer فعلًا يوفّر Operation Recorder لتسجيل touch وtext input وإعادة التشغيل loop/auto-execution، وهذا قد يكون مفيدًا جدًا عمليًا. لكن لا يوجد في التوثيق ما يثبت أنه **الحل الوحيد** أو أنه **100%** أو أنه سيتجاوز أي منطق تحقق داخل التطبيق. [Source](https://www.ldplayer.net/blog/how-to-use-operation-recorder.html)

### 4) عبارة: “ده Anti-Bot Protection مؤكدة”
دي أيضًا **غير مثبتة من الأدلة المطروحة**.
واتساب يذكر بالفعل أنه يحارب automated behavior وbulk messaging، ويذكر أيضًا أنه يحاول اكتشاف النسخ المعدلة من واتساب. لكن هذا **لا يثبت** أن السلوك الذي رأيته تحديدًا هو redirect مقصود للفوكس أو آلية منع بعينها داخل `com.WhatsApp2Plus`. # WhatsApp2Plus "Next" Button — Why All 20 Methods Failed

The fact that **every single input method failed** — including raw ADB taps, key events, and accessibility actions — tells us something very specific: this isn't a click problem. It's an **anti-automation defense**.

WhatsApp (and especially modded versions like WhatsApp2Plus / WhatsApp Plus) actively detects and blocks automated input. Let me break down what's happening and give you real solutions.

---

## Why Your Clicks Are Being Ignored

WhatsApp uses several detection mechanisms:

| Detection | What It Catches |
|---|---|
| `MotionEvent.FLAG_WINDOW_IS_OBSCURED` | ADB/uiautomator2 injected events have flags real fingers don't |
| `View.setFilterTouchesWhenObscured(true)` | The Next button literally rejects synthetic touches |
| `InputDevice.SOURCE` check | Real touches come from `SOURCE_TOUCHSCREEN`; ADB comes from a virtual device |
| Accessibility service detection | Detects `uiautomator` running and disables critical buttons |
| Focus / IME state validation | Button only "really" enables when keyboard interaction is real |

Your logs prove this — the button **exists, is visible, is green**, but ignores every input type. That's a textbook obscured-touch filter.

---

## Solutions (Ranked by Likelihood of Success)

### ✅ Solution 1: Disable `setFilterTouchesWhenObscured` via Magisk/Root
On a rooted emulator, hook the View flag:
```bash
adb shell settings put global block_untrusted_touches 0
adb shell settings put secure block_untrusted_touches 0
```
Run this **before** launching WhatsApp2Plus. This is the single most likely fix.

### ✅ Solution 2: Use `minitouch` / `scrcpy` Instead of `input tap`
`uiautomator2` and `adb input` both inject events that carry the "obscured" flag. **`minitouch`** injects at the kernel level via `/dev/input/event*` — indistinguishable from a real finger.

```python
# uiautomator2 has built-in minitouch support
d.touch.down(960, 1010)
time.sleep(0.05)
d.touch.up(960, 1010)
```
If that still uses the high-level API, try the raw approach:
```bash
adb shell sendevent /dev/input/event2 3 53 960
adb shell sendevent /dev/input/event2 3 54 1010
adb shell sendevent /dev/input/event2 1 330 1
adb shell sendevent /dev/input/event2 0 0 0
adb shell sendevent /dev/input/event2 1 330 0
adb shell sendevent /dev/input/event2 0 0 0
```

### ✅ Solution 3: Stop the uiautomator2 Service Before Clicking
WhatsApp detects `com.github.uiautomator` running on the device. Try:
```python
self.d.shell("am force-stop com.github.uiautomator")
self.d.shell("am force-stop com.github.uiautomator.test")
time.sleep(1)
# Now use raw ADB input — but this kills your u2 connection
```
Better: rename the uiautomator2 server APK before installing (advanced).

### ✅ Solution 4: Validate the Phone Number Was Actually Entered
Your `ensure_ready()` only types **one digit** (`phone[-1]`). The Next button might be **green but logically disabled** because the number is incomplete.

Replace this:

### ✅ Solution 5: Check If The Button Is Actually Clickable
Add this diagnostic before your test loop:
```python
btn = self.d(resourceId=f"{self.package}:id/registration_submit")
```

If `clickable=False` or `enabled=False`, **no click method will ever work** — you must fix the precondition (the phone number, country code, or checkbox).

```python
def ensure_ready(self, phone="1234567890"):

    if field.exists:
        # أمسح اللي مكتوب وأدخل الرقم الجديد
        field.clear_text()

    self.d.press("back")   # أو d.shell('input keyevent 111')

    if btn.exists:
        # التأكد إن الزر متاح للضغط
        if btn.info.get('enabled') and btn.info.get('clickable'):
            logger.info("Button is enabled and ready!")
            return True
        else:

    return False
```

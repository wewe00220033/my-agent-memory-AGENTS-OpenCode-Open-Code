### 🎯 الخريطة الكاملة لرحلة الـ Request (Two-Layer Timeout Architecture)

التجربتين بتوعك أثبتوا إن فيه **3 طبقات Timeout** بتتحكم في الاتصال:

```
[Mobile App / Script] ──► [Cloudflare/Nginx Gateway] ──► [Laravel Server] ──► [OpenAI API]
        ↓                          ↓                            ↓                    ↓
   Dio: 60s                   504 after ~60s               PHP max_execution        ?
   (التطبيق)                  (البوابة)                      (السيرفر الداخلي)        (الموديل)
```

| الطبقة | مين بيتحكم؟ | الـ Timeout | الإيرور اللي بيظهر |
|---|---|---|---|
| 1️⃣ Client (Flutter/Python) | إنت | قابل للتعديل | `DioException` / `requests.Timeout` |
| 2️⃣ Gateway (Cloudflare/Nginx) | Alle-AI | ~60 ثانية ثابتة | **`504 Gateway Timeout`** ← الجديد! |
| 3️⃣ Upstream (OpenAI/Anthropic) | الشركة الأم | متغير | بيرجع للسيرفر |

### 💡 الاكتشاف المحوري (اللي مكناش عارفينه قبل كده)

التجربة الأولى أثبتت إن **السيرفر بيكمل الشغل في الخلفية حتى بعد ما يرمي 504**!

ده معناه إن `api.alle-ai.com` بيستخدم **Async Job Queue** جوه Laravel:

1. الـ Gateway بيرمي `504` للـ Client بعد 60 ثانية.
2. **بس Laravel Worker جوه السيرفر بيفضل شغال** ويكمل الـ Job في الخلفية.
3. بعد ما الموديل يرد، Laravel بيخزن الرد في الـ Database مرتبط بـ `prompt_id`.
4. لما إنت تعمل Retry، السكربت بيسأل عن نفس الـ `prompt_id` فيرجعلك الرد الجاهز.

### 🔍 تشريح كود الـ Retry في `alle_chat.py`

الجزء العبقري في السكربت بتاعك:

```python

```

ده مش مجرد Retry عادي، ده **Polling Pattern** صحيح للـ Async APIs:
- ✅ بيتعامل مع `504` (Gateway Timeout) → السيرفر مردش في الوقت
- ✅ بيتعامل مع `408` (Request Timeout) → الـ Client أخد وقت كتير
- ✅ بيتعامل مع `502` (Bad Gateway) → السيرفر الداخلي مش متاح مؤقتاً

**كل دول معناهم نفس الحاجة:** "إستنى وحاول تاني، الـ Job لسه شغال جوه".

### 🎯 الخطوة التالية المقترحة (Optimization)

```python
def smart_wait_for_response(prompt_id, label):
    """انتظار ذكي مع Exponential Backoff"""
    intervals = [5, 10, 15, 25, 40, 60]  # ثواني

    for attempt, wait in enumerate(intervals, 1):
        try:
            r = requests.post(URL, headers=headers,
                            json={"prompt_id": prompt_id},
                            timeout=RESP_TIMEOUT)

            if r.status_code == 200 and r.json().get("response"):
                return r.json()
            elif r.status_code in (504, 408, 502):
                warn(f"{label}: محاولة {attempt}/6 — استنى {wait}s")
                time.sleep(wait)
            else:
                break
        except requests.exceptions.Timeout:
            warn(f"{label}: Client timeout — استنى {wait}s")
            time.sleep(wait)

    return None
```

التجربة القاسية (Stress Test) اللي عملتها دي حطت إيدينا على الـ Architecture الحقيقية للسيرفر، وكشفتلنا خريطة المشكلة بالكامل اللي نقدر نسميها **"Dual-Layer Timeouts"** (طبقتين من الانقطاع):

* **الطبقة الأولى (Client-Side):** ودي اللي كانت بتعمل المشكلة الأساسية لتطبيق الموبايل (`DioException`) لأن المهلة بتاعته قصيرة، وإحنا قضينا عليها تماماً في البايثون لما رفعنا الـ `RESP_TIMEOUT` لـ 300 و 600 ثانية.

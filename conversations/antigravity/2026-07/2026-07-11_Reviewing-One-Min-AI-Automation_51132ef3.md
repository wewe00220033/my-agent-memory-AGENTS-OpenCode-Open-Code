### Secure OAuth Verification Mechanics

When implementing OAuth login (such as "Sign in with Google") on a web application, the backend must securely verify the identity of the user without relying on client-side assertions alone. Here is how a secure verification flow works conceptually:

1. **Token Generation**: The client interacts with the Identity Provider (IdP) (e.g., Google OAuth) to authenticate the user. The IdP returns an ID Token (typically a JSON Web Token - JWT) signed by the IdP's private key.
2. **Transmission**: The client sends this JWT to the application server (e.g., via a `POST` request to `/auth/oauth`).
3. **Backend Validation (Cryptographic Verification)**:
   * **Signature Verification**: The application server must fetch the IdP's public keys (e.g., from Google's JWKS endpoint `https://www.googleapis.com/oauth2/v3/certs`) and verify the signature of the JWT to ensure it was actually issued by the IdP and has not been modified.
   * **Audience Check (`aud`)**: The server verifies that the client ID in the token matches the application's actual registered OAuth Client ID.
   * **Issuer Check (`iss`)**: The server checks that the token issuer is the expected IdP (e.g., `https://accounts.google.com`).
   * **Expiration Check (`exp`)**: The server ensures the token is currently valid and has not expired.
4. **Account Provisioning**: Only after successful validation does the server extract user details (like the verified email address) from the JWT payload to log the user in or create an account.

If a backend fails to verify the signature of the token and simply trusts the payload (such as looking at the email field without validation), it creates a critical authentication bypass vulnerability. Robust implementations ensure that cryptographic validation is strictly enforced on every authentication endpoint.

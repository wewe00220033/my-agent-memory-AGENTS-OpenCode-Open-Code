# 3. الخطر الأمني الحرج: رمز GitHub مكشوف

يوجد Personal Access Token مكتوب مباشرة في:

```python
GITHUB_TOKEN = "..."
```

وقد أصبح ظاهرًا في النص المرسل أيضًا. يجب التعامل معه على أنه **مخترق حتى لو كان المستودع خاصًا**.

## الإجراء الفوري

1. **إلغاء الرمز Revoke فورًا من GitHub**، وليس فقط حذفه من الملف.
2. إنشاء رمز جديد، ويفضل:
   - Fine-grained personal access token.
   - مقيّدًا بمستودع واحد فقط.
   - بأقل الصلاحيات اللازمة، غالبًا `Contents: Read and write`.
   - بتاريخ انتهاء قصير.
3. فحص المستودع وتاريخه لمعرفة هل تم رفع السكربت الذي يحتوي على الرمز.
4. مراجعة:
   - سجل تدقيق الحساب إن توفر.
   - آخر commits وعمليات push.
   - الأجهزة والجلسات غير المعروفة.
   - Secret scanning وتنبيهات الأمان.

GitHub يوصي بأن تكون الخطوة الأولى عند كشف سر هي **إلغاؤه أو تدويره**؛ حذف النص وحده لا يكفي:
[GitHub — Removing sensitive data](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/removing-sensitive-data-from-a-repository)

كحد أدنى يجب أن يكون `origin` رابطًا نظيفًا لا يحتوي على أي اعتماد، وألا يطبع `run_cmd` القيم الحساسة عند الفشل.

# 4. تحذير `DeprecationWarning` الخاص بـ TAR

التحذير:

```text
DeprecationWarning: Python 3.14 will, by default, filter extracted tar archives...
```

ليس خطأً، ولم يمنع العمليات الحالية من النجاح. لكنه يشير إلى أن:

```python
tar.extractall(path=extract_dir)
```

لا يحدد سياسة فك الضغط صراحةً.

في Python 3.14 أصبح الفلتر الافتراضي `data`، وهو يمنع عدة حالات خطرة، مثل:

- المسارات المطلقة.
- الملفات التي تحاول الخروج من مجلد الاستخراج عبر `../`.
- روابط تش تشير إلى خارج الوجهة.
- بعض أنواع الملفات الخاصة والخطرة.

## التعديل المطلوب

مع Python 3.13 الحالي يمكن استخدام:

```python
tar.extractall(path=extract_dir, filter="data")
```

وهذا يزيل التحذير ويجعل السلوك الأمني صريحًا ومتوافقًا مع الاتجاه الجديد.

توثيق Python يوصي بتحديد `filter='data'` خصوصًا للإصدارات الأقدم من 3.14:
[Python — tarfile extraction filters](https://docs.python.org/3/library/tarfile.html#tarfile.TarFile.extractall)

### تنبيه إضافي

حتى `filter="data"` لا يحمي من كل شيء. ينبغي أيضًا فرض حدود على:

- الحجم الإجمالي بعد فك الضغط.
- عدد الملفات.
- حجم الملف الواحد.
- عمق المجلدات.
- الأسماء الطويلة جدًا.
- الملفات المتفرقة Sparse files.
- الروابط الرمزية إذا لم تكن مطلوبة.

وذلك للحد من TAR bombs واستهلاك القرص أو الذاكرة.

# 5. مشكلة تصنيف تغييرات Git

الكود يتعامل فقط مع:

```python
if status == "A":
elif status == "M":
```

لكن `git diff --cached --name-status` قد يعيد حالات أخرى، منها:

- `D` ملف محذوف.
- `R100` ملف أعيدت تسميته.
- `C100` ملف منسوخ.
- `T` تغير نوع الملف.
- `U` تعارض.
- حالات متعددة الأحرف.

## المشكلة الأخطر

شرط وجود تغييرات هو:

```python
if not new_files and not updated_files:
```

وبالتالي لو كانت التغييرات الوحيدة:

- حذف ملفات فقط.
- إعادة تسمية فقط.
- تغير نوع ملف فقط.

فسيتعامل السكربت معها على أنها:

```text
لا توجد أي تغييرات
```

ولن ينشئ commit أو push، مع أن `diff_out` ليس فارغًا والتغييرات staged فعلًا.

### المطلوب

- تحديد وجود التغييرات من `diff_out` نفسه أو من نتيجة `git diff --cached --quiet`.
- تصنيف كل الحالات، بما فيها الحذف وإعادة التسمية.
- إيقاف التنفيذ عند وجود `U` أو حالة غير معروفة بدل تجاهلها.
- تضمين المحذوف والمعاد تسميته في التقرير ورسالة commit.

# 6. النسخ الحالي Overlay وليس مزامنة كاملة

الدالة:

```python
copy_tree(source_root, clone_dir)
```

تنسخ الملفات الجديدة وتستبدل الموجودة، لكنها **لا تحذف من المستودع الملفات التي لم تعد موجودة في الأرشيف**.

مثال:

- المستودع يحتوي `old.py`.
- الأرشيف الجديد لا يحتوي `old.py`.
- بعد `copy_tree` سيظل `old.py` موجودًا في `clone_dir`.
- وبالتالي لن يسجله Git كملف محذوف.

هذا يعني أن الناتج على GitHub قد يصبح خليطًا من النسخة القديمة والجديدة، وليس مرآة مطابقة للأرشيف.

## القرار المطلوب

يجب تحديد السلوك المقصود:

- إذا المطلوب **Overlay/update فقط**، فالسلوك الحالي مقبول لكن يجب توثيقه.
- إذا المطلوب **أن يصبح GitHub مطابقًا تمامًا للأرشيف**، فيجب تنظيف محتوى working tree — مع الحفاظ على `.git` والملفات المستثناة المقصودة — ثم نسخ المصدر.

ويفضل تنفيذ ذلك بقائمة سماح واضحة لتجنب حذف ملفات مستودع مهمة مثل إعدادات CI أو ملفات الحماية.

# 8. التقرير لا يُرفع إلى GitHub

# 9. حذف الأرشيف بعد الرفع

السلوك الحالي إيجابي جزئيًا:

- إذا فشل clone أو commit أو push، يُرفع استثناء، وبالتالي لا يصل التنفيذ إلى حذف الأرشيف.
- التنظيف المؤقت يجري عبر `finally`.

لكن بعد ظهور نجاح push ونجاح كتابة التقرير، يُحذف الأرشيف فورًا. يفضل عدم الحذف قبل التحقق من:

- أن SHA المحلي هو نفسه SHA الموجود على `origin/main`.
- أن الملفات الأساسية موجودة في النسخة البعيدة.
- أن الاختبارات نجحت.
- أن التقرير كُتب فعلًا وتم عمل `flush/fsync` إذا كانت الموثوقية مهمة.

والأفضل دعم خيارات مثل:

- `--delete-after-success`
- `--keep-archive`
- نقل الأرشيف إلى مجلد `processed/` بدل حذفه نهائيًا.
- الاحتفاظ به مدة زمنية قبل التنظيف.

# 10. لا توجد اختبارات قبل الدفع إلى `main`

السكربت يدفع مباشرة إلى:


دون:

- فحص أسرار.

## المسار الأكثر أمانًا

إذا كان الدفع المباشر مطلوبًا، فيجب على الأقل طباعة ملخص دقيق وطلب تأكيد، أو توفير `--yes` للتشغيل غير التفاعلي.

# 11. ملاحظات فنية إضافية

### `decode_git_path`

بعد ضبط:

```python
git config core.quotepath false
```

غالبًا لا تكون سلسلة فك الترميز اليدوية ضرورية، وقد تُفسد بعض الأسماء غير المعتادة. الحل الأكثر متانة هو استخدام مخرجات Git المنتهية بـNUL مثل `-z` ثم تحليلها كبايتات بدل الاعتماد على الأسطر والمسافات.

### اختيار الأرشيف الأحدث تلقائيًا

عند وجود أكثر من ملف، يختار السكربت الأحدث. هذا مريح لكنه قد يرفع ملفًا غير مقصود. يفضل:

- طباعة جميع المرشحين.
- اشتراط معامل صريح في وضع الإنتاج.
- أو توفير `--latest` كخيار واضح بدل أن يكون سلوكًا ضمنيًا.

### التنظيف الصامت

```python
shutil.rmtree(temp_dir, ignore_errors=True)
```

ثم دائمًا:

```text
تم التنظيف بالكامل.
```

حتى لو فشل الحذف. هذه الرسالة قد تكون غير صحيحة. يجب التحقق من أن المجلد اختفى، وإن بقي، تسجيل تحذير ومساره — خصوصًا لأن النسخة المؤقتة قد تحتوي حاليًا على رمز الاعتماد داخل `.git/config`.

### هوية Git

نجاح commits الحالية يعني غالبًا أن `user.name` و`user.email` مهيآن عالميًا. لكن الأفضل التحقق منهما أو تعيين هوية bot محلية داخل المستودع المؤقت.

8. تحديد هل النسخ Overlay أم مزامنة مطابقة.
9. إصلاح اكتشاف جذر المصدر وعدم الاعتماد على أي اسم يحتوي `clone`.
10. التحقق من remote SHA بعد push وقبل حذف الأرشيف.

## تحسينات تشغيلية

11. إضافة إصدار وhash للسكربت إلى السجل.
12. تسجيل SHA للـcommit في التيرمينال، وليس في التقرير فقط.
13. عدم الادعاء بأن التنظيف اكتمل قبل التحقق.
14. تشغيل اختبارات وفحص أسرار قبل push.
15. الدفع إلى فرع وPull Request بدل `main`.
16. إضافة `dry-run` يعرض الملفات التي ستضاف أو تعدل أو تحذف دون commit أو push.

## الحكم النهائي

- **هل عمليات الرفع نجحت؟** وفق الرسائل الظاهرة: نعم، كل التشغيلات المعروضة أعلنت نجاح `git push` ثم التقرير والحذف والتنظيف.
- **هل توجد أخطاء قاتلة؟** لا تظهر أخطاء قاتلة أو `Traceback`.
- **هل `DeprecationWarning` منع التنفيذ؟** لا، لكنه يستلزم تعديلًا أمنيًا واضحًا.
- **هل يمكن اعتبار النظام آمنًا وسليمًا بالكامل؟** لا؛ رمز GitHub المكشوف هو أخطر مشكلة، ثم فك TAR دون فلتر صريح، ثم قصور تصنيف تغييرات Git وعدم تطابق بعض السجلات مع الكود الحالي.
- **هل حُذف المصدر المضغوط؟** نعم حسب السجلات، بعد كل عملية معروضة.
- **هل التقرير رُفع إلى GitHub؟** لا؛ وفق الكود هو تقرير محلي يُكتب بجانب الأرشيف بعد انتهاء الـpush.

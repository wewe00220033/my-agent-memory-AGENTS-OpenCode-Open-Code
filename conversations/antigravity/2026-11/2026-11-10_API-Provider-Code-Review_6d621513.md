## 2. ⚠️ الحالات الحدية والمشكلات المنطقية

### أ. المشروع الضخم

لا يوجد حالياً أي حد لـ:

- حجم الملف الواحد.
- إجمالي حجم الملفات.
- إجمالي عدد الملفات.
- حجم الـ Diff.
- زمن قراءة الملفات أو تنفيذ Git.

الأسوأ أن النص يتكرر في الذاكرة عدة مرات:

1. محتوى كل ملف.
2. قائمة `output`.
-3. الناتج من `"\n".join(output)`.
4. `full_text`.
5. نسخة UTF-8 أثناء الإرسال إلى PowerShell.
6. نسخة UTF-16 داخل Windows Clipboard.
7. نسخ داخل عملية PowerShell نفسها.

لذلك قد يستهلك تشغيل السكريبت عدة أضعاف الحجم الظاهر للحزمة. لا توجد «سعة حافظة» صغيرة ثابتة يمكن الاعتماد عليها؛ القيود العملية هي الذاكرة، ومهلة العملية، وقفل الحافظة، ثم **حد سياق نموذج الذكاء الاصطناعي نفسه**.

الحل الصحيح ليس محاولة نسخ 500MB، بل:

- وضع حد أقصى للملف والحزمة.
- إيقاف العملية بوضوح أو إنشاء ملف فقط.
- التقسيم إلى دفعات ذات حدود مستقلة.
- تفضيل Diff أو الملفات المتأثرة على إرسال المشروع كاملاً.

### ثانياً: الملفات الثنائية والملفات النصية الضخمة

الامتداد وحده لا يكفي:

- ملف `.js` قد يكون Bundle minified بحجم عشرات الميجابايت.
- ملف `.sql` قد يكون Dump ضخماً.
- ملف `.json` قد يكون Blob أو تقريراً ضخماً.
- ملف بامتداد `.py` قد يكون تالفاً أو ثنائياً عملياً.
- `errors="replace"` يمنع الانهيار، لكنه **لا يمنع تلويث السياق**؛ سيستبدل البايتات غير الصالحة بـ`�` ويستمر في الحزم.

المطلوب فحص الحجم والبايتات قبل القراءة، ورفض NUL bytes ونسب المحارب غير النصية المرتفعة.

### ثالثاً: دلالات Git الحالية غير صحيحة

هذه من أهم مشاكل السكريبت:

```python
has_uncommitted = bool(status_proc.stdout.strip())
```

ثم:

```python
if has_uncommitted:
    git diff
else:
    git diff HEAD~1
```

النتائج:

| حالة المستودع | النتيجة الحالية |
|---|---|
| تعديلات Staged فقط | `has_uncommitted=True`، لكن `git diff` لا يعرض staged changes؛ قد تحصل على Diff فارغ |
| ملفات Untracked فقط | يكتشف وجود تغييرات، لكن `git diff` لا يعرض محتواها |
| Staged + Unstaged | قد يعرض غير الم staged فقط، فيضيع جزء من العمل |
| لا تعديلات | يعرض diff آخر commit مقابل `HEAD~1`، وهذا سلوك مختلف تماماً |
| أول Commit في المستودع | `HEAD~1` غير موجود؛ الدالة تعيد غالباً نصاً فارغاً بدلاً من خطأ واضح |
| مستودع غير موجود أو Git مفقود | قد تتحول الأخطاء إلى رسالة «لا توجد فروقات» |
| Merge Conflict | لا يوجد فحص؛ قد يخرج Diff يتضمن conflict markers أو `Unmerged paths` |
| Detached HEAD | ليست مشكلة بذاتها؛ `HEAD` و`HEAD~1` يعملان عادةً، لكن `HEAD~1` يفشل إذا لم يوجد أب أو كان العمق غير كافٍ |
| شallow clone | قد يفشل `HEAD~1` لأن التاريخ غير متوفر محلياً |

كما أن `git -C target_dir diff` قد يعرض **تغييرات المستودع كله**، لا التغييرات داخل `target_dir` فقط.

### حالات أخرى

- **Merge Conflict:** يجب إيقاف التصدير برسالة واضحة بدلاً من إرسال Diff مضلل.
- **Detached HEAD:** ليست مشكلة بحد ذاتها؛ المهم التحقق من المرجع وعدم افتراض وجود فرع.
- **عدم وجود commits:** يجب معالجة `HEAD` غير الموجود.
- **Git لا يستجيب:** لا توجد `timeout`.
- **Clipboard مشغول:** قد يفشل `OpenClipboard` بسبب تطبيق آخر.
- **فشل النسخ:** السكريبت يطبع رسائل النجاح رغم أن `success` قد تكون `False`.
- **فشل الكتابة إلى `--out`:** قد يحدث استثناء غير معالج أو يفسد ملفاً موجوداً؛ والكتابة ليست ذرية.

## 3. ⚡ ضعف `PowerShell Set-Clipboard` والبديل

نقاط الضعف في التنفيذ الحالي:

1. إطلاق PowerShell عملية مكلفة نسبياً في كل مرة.
2. لا يوجد `timeout`؛ يمكن أن يبقى `communicate()` معلقاً.
3. `$input | Set-Clipboard` يمر عبر Pipeline ومفسر PowerShell، وليس مجرد نسخ Buffer.
4. توجد نسخ متعددة للنص في الذاكرة: Python، UTF-8 Pipe، PowerShell strings، ثم UTF-16 Clipboard.
5. قفل الحافظة من تطبيق آخر قد يسبب فشلاً متقطعاً، ولا توجد إعادة محاولة.
6. `stderr` غير متصل بشكل جيد، ولا يوجد Timeout عند الانتظار.
7. رسالة النجاح تظهر حتى لو فشل النسخ، لأن قيمة `success` لا تؤثر على النتيجة.

### البديل الأفضل

على Windows استخدم **Win32 Clipboard API مباشرة** عبر `pywin32`، مع:

- `CF_UNICODETEXT`.
- إعادة المحاولة عند انشغال الحافظة.
- `try/finally` لضمان `CloseClipboard`.
- حفظ الملف أولاً، ثم محاولة الحافظة.
- حد أقصى واضح للحافظة، وعند تجاوزه: ملف فقط أو تقسيم صريح.

```python
# pip install pywin32
import time
import win32clipboard
import pywintypes


def copy_to_clipboard(text: str, attempts: int = 6) -> None:
    """Raise on failure; never report a false success."""
    last_error = None

    for attempt in range(attempts):
        opened = False
        try:
            win32clipboard.OpenClipboard()  # يفشل غالباً إذا كانت الحافظة محجوزة
            opened = True
            win32clipboard.EmptyClipboard()
            win32clipboard.SetClipboardData(
                win32clipboard.CF_UNICODETEXT,
                text,
            )
            return
        except pywintypes.error as exc:
            last_error = exc
            time.sleep(0.05 * (2 ** attempt))
        finally:
            if opened:
                win32clipboard.CloseClipboard()

    raise RuntimeError(f"Clipboard is busy or unavailable: {last_error}")
```

> للنصوص الكبيرة جداً، حتى Win32 لن يحل مشكلة الذاكرة أو حدود سياق النموذج. الحل المعماري هو **وضع سقف، والتقسيم إلى دفعات، أو استخدام الملف كبديل**، لا محاولة حشر الحزمة كلها في الحافظة.

```python
    path.parent.mkdir(parents=True, exist_ok=True)
```

```python
        "--no-color",
        "--no-ext-diff",
        "--no-textconv",
        "--binary",
```

### النتائج الفعلية

| الحالة | النتيجة الحالية |
|---|---|
| تعديلات staged فقط | `has_uncommitted=True`، ثم `git diff` الذي لا يعرض staged changes؛ قد يكون الناتج فارغاً |
| تعديلات staged + unstaged | يعرض غير الم staged فقط، فيضيع جزء من العمل |
| ملفات untracked فقط | يعتبر أن هناك تغييرات، لكن `git diff` لا يعرض محتواها |
| لا تعديلات | يعرض `HEAD~1`، أي اختلاف شجرة العمل الحالية عن `HEAD~1`، وليس دائماً «آخر commit فقط» |
| أول commit أو لا يوجد `HEAD~1` | يفشل Git، لكن السكريبت قد يحوله إلى رسالة «لا توجد فروقات» |
| Merge Conflict | لا يوجد فحص؛ قد ينتج Diff مضللاً |
| Detached HEAD | ليست مشكلة بذاتها، لكن `HEAD~1` قد يفشل إذا لم يوجد الأب أو التاريخ غير متوفر |
| Git غير مثبت أو المسار ليس مستودعاً | لا يتم فحص `returncode` أو `stderr` بصورة صحيحة |

كما أن `git -C target_dir diff` يعيد تغييرات **المستودع كله**، وليس بالضرورة التغييرات الواقعة داخل `target_dir` فقط.

الأفضل تحديد دلالات واضحة:

- `--diff`: التغييرات staged + unstaged منذ `HEAD`.
- `--since REV`: التغييرات منذ مرجع محدد.
- `--last-commit`: آخر commit وحده عبر `git show` أو `git diff HEAD~1 HEAD`.
- إظهار الملفات untracked بوضوح، أو تضمينها بسياسة مستقلة.

```python
import os
import time


def copy_to_clipboard(text: str, attempts: int = 6) -> None:
    if os.name != "nt":
        raise RuntimeError("Automatic clipboard copy is supported on Windows only.")

    import pywintypes
    import win32clipboard

    last_error = None

    for attempt in range(attempts):
        opened = False
        try:
            win32clipboard.OpenClipboard()  # لا تعط HWND تملكه
            opened = True
            win32clipboard.EmptyClipboard()
            win32clipboard.SetClipboardData(
                win32clipboard.CF_UNICODETEXT,
                text,
            )
            return
        except pywintypes.error as exc:
            last_error = exc
            time.sleep(0.05 * (2 ** attempt))
        finally:
            if opened:
                try:
                    win32clipboard.CloseClipboard()
                except Exception:
                    pass

    raise RuntimeError(f"Clipboard is busy or unavailable: {last_error}")
```

## ب. قراءة ذات حدود وكشف الثنائيات

```python
MAX_FILE_BYTES = 2 * 1024 * 1024
MAX_TOTAL_BYTES = 8 * 1024 * 1024


def read_text_safely(path: Path) -> str:
    if path.is_symlink():
        raise ValueError("Symbolic links are not exported")

    size = path.stat().st_size
    if size > MAX_FILE_BYTES:
        raise ValueError(f"file exceeds {MAX_FILE_BYTES} bytes")

    with path.open("rb") as stream:
        data = stream.read(MAX_FILE_BYTES + 1)

    if len(data) > MAX_FILE_BYTES:
        raise ValueError("file exceeds size limit")

    sample = data[:8192]
    if b"\x00" in sample:
        raise ValueError("binary file rejected")

    if sample:
        allowed = set(b"\n\r\t\f\b")
        control = sum(
            byte < 32 and byte not in b"\n\r\t\f\b"
            for byte in sample
        )
        if control / len(sample) > 0.10:
            raise ValueError("probably binary")
```

```python
    pass


def run_git(repo: Path, *args: str, timeout: int = 30) -> str:
    try:
        proc = subprocess.run(
            ["git", "-C", str(repo), *args],
            stdout=subprocess.PIPE,
            stderr=subprocess.PIPE,
            text=True,
            encoding="utf-8",
            errors="replace",
            timeout=30,

        raise RuntimeError("Git executable was not found.") from exc
    except subprocess.TimeoutExpired as exc:
        raise RuntimeError("Git command timed out.") from exc

    if proc.returncode != 0:
        raise RuntimeError(proc.stderr.strip() or "Git command failed.")

def get_git_diff(target_dir: Path, base: str = "HEAD") -> str:
    if run_git(target_dir, "ls-files", "-u").strip():
        raise RuntimeError(
            "Repository has unresolved merge conflicts; resolve them first."
        )

            f"Cannot resolve base revision {base!r}. "
            "Use --since with a valid commit."

        target_dir,
```

### ثانياً: الملفات الثنائية والملفات النصية الضخمة

الامتداد وحده لا يكفي:

### ثالثاً: دلالات Git الحالية غير صحيحة

هذه من أهم مشاكل السكريبت:

```python

```

ثم:

```python

    git diff

```

النتائج:

| حالة المستودع | النتيجة الحالية |
|---|---|
| تعديلات Staged فقط | `has_uncommitted=True`، لكن `git diff` لا يعرض staged changes؛ قد تحصل على Diff فارغ |
| ملفات Untracked فقط | يكتشف وجود تغييرات، لكن `git diff` لا يعرض محتواها |
| Staged + Unstaged | قد يعرض غير الم staged فقط، فيضيع جزء من العمل |
| لا تعديلات | يعرض diff آخر commit مقابل `HEAD~1`، وهذا سلوك مختلف تماماً |
| أول Commit في المستودع | `HEAD~1` غير موجود؛ الدالة تعيد غالباً نصاً فارغاً بدلاً من خطأ واضح |
| مستودع غير موجود أو Git مفقود | قد تتحول الأخطاء إلى رسالة «لا توجد فروقات» |
| Merge Conflict | لا يوجد فحص؛ قد يخرج Diff يتضمن conflict markers أو `Unmerged paths` |
| Detached HEAD | ليست مشكلة بذاتها؛ `HEAD` و`HEAD~1` يعملان عادةً، لكن `HEAD~1` يفشل إذا لم يوجد أب أو كان العمق غير كافٍ |
| شallow clone | قد يفشل `HEAD~1` لأن التاريخ غير متوفر محلياً |

كما أن `git -C target_dir diff` قد يعرض **تغييرات المستودع كله**، لا التغييرات داخل `target_dir` فقط.

### حالات أخرى

- **Merge Conflict:** يجب إيقاف التصدير برسالة واضحة بدلاً من إرسال Diff مضلل.
- **Detached HEAD:** ليست مشكلة بحد ذاتها؛ المهم التحقق من المرجع وعدم افتراض وجود فرع.
- **عدم وجود commits:** يجب معالجة `HEAD` غير الموجود.
- **Git لا يستجيب:** لا توجد `timeout`.
- **Clipboard مشغول:** قد يفشل `OpenClipboard` بسبب تطبيق آخر.
- **فشل النسخ:** السكريبت يطبع رسائل النجاح رغم أن `success` قد تكون `False`.
- **فشل الكتابة إلى `--out`:** قد يحدث استثناء غير معالج أو يفسد ملفاً موجوداً؛ والكتابة ليست ذرية.

## 3. ⚡ ضعف `PowerShell Set-Clipboard` والبديل

نقاط الضعف في التنفيذ الحالي:

1. إطلاق PowerShell عملية مكلفة نسبياً في كل مرة.
2. لا يوجد `timeout`؛ يمكن أن يبقى `communicate()` معلقاً.
3. `$input | Set-Clipboard` يمر عبر Pipeline ومفسر PowerShell، وليس مجرد نسخ Buffer.
4. توجد نسخ متعددة للنص في الذاكرة: Python، UTF-8 Pipe، PowerShell strings، ثم UTF-16 Clipboard.
5. قفل الحافظة من تطبيق آخر قد يسبب فشلاً متقطعاً، ولا توجد إعادة محاولة.
6. `stderr` غير متصل بشكل جيد، ولا يوجد Timeout عند الانتظار.
7. رسالة النجاح تظهر حتى لو فشل النسخ، لأن قيمة `success` لا تؤثر على النتيجة.

### البديل الأفضل

على Windows استخدم **Win32 Clipboard API مباشرة** عبر `pywin32`، مع:

- `CF_UNICODETEXT`.
- إعادة المحاولة عند انشغال الحافظة.
- `try/finally` لضمان `CloseClipboard`.
- حفظ الملف أولاً، ثم محاولة الحافظة.
- حد أقصى واضح للحافظة، وعند تجاوزه: ملف فقط أو تقسيم صريح.

```python
# pip install pywin32
import time
import win32clipboard
import pywintypes


def copy_to_clipboard(text: str, attempts: int = 6) -> None:
    """Raise on failure; never report a false success."""
    last_error = None

    for attempt in range(attempts):
        opened = False
        try:
            win32clipboard.OpenClipboard()  # يفشل غالباً إذا كانت الحافظة محجوزة
            opened = True
            win32clipboard.EmptyClipboard()
            win32clipboard.SetClipboardData(
                win32clipboard.CF_UNICODETEXT,
                text,
            )
            return
        except pywintypes.error as exc:
            last_error = exc
            time.sleep(0.05 * (2 ** attempt))
        finally:
            if opened:
                win32clipboard.CloseClipboard()

    raise RuntimeError(f"Clipboard is busy or unavailable: {last_error}")
```

> للنصوص الكبيرة جداً، حتى Win32 لن يحل مشكلة الذاكرة أو حدود سياق النموذج. الحل المعماري هو **وضع سقف، والتقسيم إلى دفعات، أو استخدام الملف كبديل**، لا محاولة حشر الحزمة كلها في الحافظة.

```python
    if secret_pattern.search(text):
```

## أ. المشاريع الضخمة والملفات الثنائية

حالياً يتم:



### النتائج الفعلية

| الحالة | النتيجة الحالية |
|---|---|
| تعديلات staged فقط | `has_uncommitted=True`، ثم `git diff` الذي لا يعرض staged changes؛ قد يكون الناتج فارغاً |
| تعديلات staged + unstaged | يعرض غير الم staged فقط، فيضيع جزء من العمل |
| ملفات untracked فقط | يعتبر أن هناك تغييرات، لكن `git diff` لا يعرض محتواها |
| لا تعديلات | يعرض `HEAD~1`، أي اختلاف شجرة العمل الحالية عن `HEAD~1`، وليس دائماً «آخر commit فقط» |
| أول commit أو لا يوجد `HEAD~1` | يفشل Git، لكن السكريبت قد يحوله إلى رسالة «لا توجد فروقات» |
| Merge Conflict | لا يوجد فحص؛ قد ينتج Diff مضللاً |
| Detached HEAD | ليست مشكلة بذاتها، لكن `HEAD~1` قد يفشل إذا لم يوجد الأب أو التاريخ غير متوفر |
| Git غير مثبت أو المسار ليس مستودعاً | لا يتم فحص `returncode` أو `stderr` بصورة صحيحة |

كما أن `git -C target_dir diff` يعيد تغييرات **المستودع كله**، وليس بالضرورة التغييرات الواقعة داخل `target_dir` فقط.

الأفضل تحديد دلالات واضحة:

- `--diff`: التغييرات staged + unstaged منذ `HEAD`.
- `--since REV`: التغييرات منذ مرجع محدد.
- `--last-commit`: آخر commit وحده عبر `git show` أو `git diff HEAD~1 HEAD`.
- إظهار الملفات untracked بوضوح، أو تضمينها بسياسة مستقلة.

```python
import os
import time


def copy_to_clipboard(text: str, attempts: int = 6) -> None:
    if os.name != "nt":
        raise RuntimeError("Automatic clipboard copy is supported on Windows only.")

    import pywintypes
    import win32clipboard

    last_error = None

    for attempt in range(attempts):
        opened = False
        try:
            win32clipboard.OpenClipboard()  # لا تعط HWND تملكه
            opened = True
            win32clipboard.EmptyClipboard()
            win32clipboard.SetClipboardData(
                win32clipboard.CF_UNICODETEXT,
                text,
            )
            return
        except pywintypes.error as exc:
            last_error = exc
            time.sleep(0.05 * (2 ** attempt))
        finally:
            if opened:
                try:
                    win32clipboard.CloseClipboard()
                except Exception:
                    pass

    raise RuntimeError(f"Clipboard is busy or unavailable: {last_error}")
```

## ب. قراءة ذات حدود وكشف الثنائيات

```python
MAX_FILE_BYTES = 2 * 1024 * 1024
MAX_TOTAL_BYTES = 8 * 1024 * 1024


def read_text_safely(path: Path) -> str:
    if path.is_symlink():
        raise ValueError("Symbolic links are not exported")

    size = path.stat().st_size
    if size > MAX_FILE_BYTES:
        raise ValueError(f"file exceeds {MAX_FILE_BYTES} bytes")

    with path.open("rb") as stream:
        data = stream.read(MAX_FILE_BYTES + 1)

    if len(data) > MAX_FILE_BYTES:
        raise ValueError("file exceeds size limit")

    sample = data[:8192]
    if b"\x00" in sample:
        raise ValueError("binary file rejected")

    if sample:
        allowed = set(b"\n\r\t\f\b")
        control = sum(
            byte < 32 and byte not in b"\n\r\t\f\b"
            for byte in sample
        )
        if control / len(sample) > 0.10:
            raise ValueError("probably binary")

    return data.decode("utf-8")
```

```python
        raise RuntimeError(proc.stderr.strip() or "Git command failed.")

    return proc.stdout


def get_git_diff(target_dir: Path, base: str = "HEAD") -> str:
    if run_git(target_dir, "ls-files", "-u").strip():
        raise RuntimeError(
            "Repository has unresolved merge conflicts; resolve them first."
        )

    # لا تشترط وجود فرع: detached HEAD حالة صالحة.
    try:
        base_commit = run_git(
            target_dir,
            "rev-parse",
            "--verify",
            f"{base}^{{commit}}",
        ).strip()
    except RuntimeError as exc:
        raise RuntimeError(
            f"Cannot resolve base revision {base!r}. "
            "Use --since with a valid commit."
        ) from exc

    # HEAD يشمل staged + unstaged؛ لا يشمل محتوى untracked.
    return run_git(
        target_dir,
        "-c", "core.quotepath=false",
        "diff",
        "--no-color",
        "--no-ext-diff",
        "--no-textconv",
        base,
        "--",
        ".",
    )
```

| حالة المستودع | النتيجة الحالية |
|---|---|
| تعديلات Staged فقط | `has_uncommitted=True`، لكن `git diff` لا يعرض staged changes؛ قد تحصل على Diff فارغ |
| ملفات Untracked فقط | يكتشف وجود تغييرات، لكن `git diff` لا يعرض محتواها |
| Staged + Unstaged | قد يعرض غير الم staged فقط، فيضيع جزء من العمل |
| لا تعديلات | يعرض diff آخر commit مقابل `HEAD~1`، وهذا سلوك مختلف تماماً |
| أول Commit في المستودع | `HEAD~1` غير موجود؛ الدالة تعيد غالباً نصاً فارغاً بدلاً من خطأ واضح |
| مستودع غير موجود أو Git مفقود | قد تتحول الأخطاء إلى رسالة «لا توجد فروقات» |
| Merge Conflict | لا يوجد فحص؛ قد يخرج Diff يتضمن conflict markers أو `Unmerged paths` |
| Detached HEAD | ليست مشكلة بذاتها؛ `HEAD` و`HEAD~1` يعملان عادةً، لكن `HEAD~1` يفشل إذا لم يوجد أب أو كان العمق غير كافٍ |
| شallow clone | قد يفشل `HEAD~1` لأن التاريخ غير متوفر محلياً |

كما أن `git -C target_dir diff` قد يعرض **تغييرات المستودع كله**، لا التغييرات داخل `target_dir` فقط.

### حالات أخرى

- **Merge Conflict:** يجب إيقاف التصدير برسالة واضحة بدلاً من إرسال Diff مضلل.
- **Detached HEAD:** ليست مشكلة بحد ذاتها؛ المهم التحقق من المرجع وعدم افتراض وجود فرع.
- **عدم وجود commits:** يجب معالجة `HEAD` غير الموجود.
- **Git لا يستجيب:** لا توجد `timeout`.
- **Clipboard مشغول:** قد يفشل `OpenClipboard` بسبب تطبيق آخر.
- **فشل النسخ:** السكريبت يطبع رسائل النجاح رغم أن `success` قد تكون `False`.
- **فشل الكتابة إلى `--out`:** قد يحدث استثناء غير معالج أو يفسد ملفاً موجوداً؛ والكتابة ليست ذرية.

### البديل الأفضل

على Windows استخدم **Win32 Clipboard API مباشرة** عبر `pywin32`، مع:

- `CF_UNICODETEXT`.
- إعادة المحاولة عند انشغال الحافظة.
- `try/finally` لضمان `CloseClipboard`.
- حفظ الملف أولاً، ثم محاولة الحافظة.

```python
# pip install pywin32
import time
import win32clipboard
import pywintypes


def copy_to_clipboard(text: str, attempts: int = 6) -> None:
    """Raise on failure; never report a false success."""
    last_error = None

    for attempt in range(attempts):
        opened = False
        try:
            win32clipboard.OpenClipboard()  # يفشل غالباً إذا كانت الحافظة محجوزة
            opened = True
            win32clipboard.EmptyClipboard()
            win32clipboard.SetClipboardData(
                win32clipboard.CF_UNICODETEXT,
                text,
            )
            return
        except pywintypes.error as exc:
            last_error = exc
            time.sleep(0.05 * (2 ** attempt))
        finally:
            if opened:
                win32clipboard.CloseClipboard()

    raise RuntimeError(f"Clipboard is busy or unavailable: {last_error}")
```

```python
        target_dir,

        "--no-color",
        "--no-ext-diff",
        "--no-textconv",
```

## ب. أخطاء منطق `get_git_diff`


### النتائج الفعلية

| الحالة | النتيجة الحالية |
|---|---|
| تعديلات staged فقط | `has_uncommitted=True`، ثم `git diff` الذي لا يعرض staged changes؛ قد يكون الناتج فارغاً |
| تعديلات staged + unstaged | يعرض غير الم staged فقط، فيضيع جزء من العمل |
| ملفات untracked فقط | يعتبر أن هناك تغييرات، لكن `git diff` لا يعرض محتواها |
| لا تعديلات | يعرض `HEAD~1`، أي اختلاف شجرة العمل الحالية عن `HEAD~1`، وليس دائماً «آخر commit فقط» |
| أول commit أو لا يوجد `HEAD~1` | يفشل Git، لكن السكريبت قد يحوله إلى رسالة «لا توجد فروقات» |
| Merge Conflict | لا يوجد فحص؛ قد ينتج Diff مضللاً |
| Detached HEAD | ليست مشكلة بذاتها، لكن `HEAD~1` قد يفشل إذا لم يوجد الأب أو التاريخ غير متوفر |
| Git غير مثبت أو المسار ليس مستودعاً | لا يتم فحص `returncode` أو `stderr` بصورة صحيحة |

كما أن `git -C target_dir diff` يعيد تغييرات **المستودع كله**، وليس بالضرورة التغييرات الواقعة داخل `target_dir` فقط.

الأفضل تحديد دلالات واضحة:

- `--diff`: التغييرات staged + unstaged منذ `HEAD`.
- `--since REV`: التغييرات منذ مرجع محدد.
- `--last-commit`: آخر commit وحده عبر `git show` أو `git diff HEAD~1 HEAD`.
- إظهار الملفات untracked بوضوح، أو تضمينها بسياسة مستقلة.

```python
import os
import time


def copy_to_clipboard(text: str, attempts: int = 6) -> None:
    if os.name != "nt":
        raise RuntimeError("Automatic clipboard copy is supported on Windows only.")

    import pywintypes
    import win32clipboard

    last_error = None

    for attempt in range(attempts):
        opened = False
        try:
            win32clipboard.OpenClipboard()  # لا تعط HWND تملكه
            opened = True
            win32clipboard.EmptyClipboard()
            win32clipboard.SetClipboardData(
                win32clipboard.CF_UNICODETEXT,
                text,
            )
            return
        except pywintypes.error as exc:
            last_error = exc
            time.sleep(0.05 * (2 ** attempt))
        finally:
            if opened:
                try:
                    win32clipboard.CloseClipboard()
                except Exception:
                    pass

    raise RuntimeError(f"Clipboard is busy or unavailable: {last_error}")
```

هذا لا يزيل الحاجة إلى حد للحجم؛ Clipboard يستخدم ذاكرة النظام، والنص يحتاج تقريباً إلى UTF-16، وقد توجد نسخ متعددة منه أثناء التجهيز.

```python
MAX_FILE_BYTES = 2 * 1024 * 1024
MAX_TOTAL_BYTES = 8 * 1024 * 1024


def read_text_safely(path: Path) -> str:
    if path.is_symlink():
        raise ValueError("Symbolic links are not exported")

    size = path.stat().st_size
    if size > MAX_FILE_BYTES:
        raise ValueError(f"file exceeds {MAX_FILE_BYTES} bytes")

    with path.open("rb") as stream:
        data = stream.read(MAX_FILE_BYTES + 1)

    if len(data) > MAX_FILE_BYTES:
        raise ValueError("file exceeds size limit")

    sample = data[:8192]
    if b"\x00" in sample:
        raise ValueError("binary file rejected")

    if sample:
        allowed = set(b"\n\r\t\f\b")
        control = sum(
            byte < 32 and byte not in b"\n\r\t\f\b"
            for byte in sample
        )
        if control / len(sample) > 0.10:
            raise ValueError("probably binary")

    return data.decode("utf-8")
```

```python
def run_git(repo: Path, *args: str, timeout: int = 30) -> str:
    try:
        proc = subprocess.run(
            ["git", "-C", str(repo), *args],
            stdout=subprocess.PIPE,
            stderr=subprocess.PIPE,
            text=True,
            encoding="utf-8",
            errors="replace",
            timeout=30,
            check=False,

    except subprocess.TimeoutExpired as exc:
        raise RuntimeError("Git command timed out.") from exc

    if proc.returncode != 0:
        raise RuntimeError(proc.stderr.strip() or "Git command failed.")

    return proc.stdout


def get_git_diff(target_dir: Path, base: str = "HEAD") -> str:
    if run_git(target_dir, "ls-files", "-u").strip():
        raise RuntimeError(
            "Repository has unresolved merge conflicts; resolve them first."

            f"Cannot resolve base revision {base!r}. "
            "Use --since with a valid commit."
        ) from exc

    return run_git(
        target_dir,
        "-c", "core.quotepath=false",

        "--no-color",
```

# 2. الثغرات والأخطاء المتبقية

## أ. خلل خطير في الـ Fallback داخل Git Diff

هذا الشرط غير صحيح:

```python
if proc.returncode != 0 or not diff_out.strip():
```

**فراغ الـ Diff ليس فشلاً.** بل هو نتيجة صحيحة تعني عدم وجود اختلافات tracked.

عندما لا توجد تغييرات، ينتقل السكريبت إلى:

```python
git diff HEAD~1 -- .
```

وهذا قد يعرض **آخر Commit**، رغم أن المستخدم طلب تغييرات شجرة العمل الحالية. كذلك إذا كان هناك ملفات untracked فقط، يكون `diff_out` فارغاً، فيضيف السكريبت diff آخر Commit بلا مبرر، ثم يضيف أسماء الملفات غير المتتبعة.

كذلك قد يخفي الفشل الحقيقي:

- `git` غير موجود.
- المسار ليس مستودعاً.
- المرجع `--since` غير صالح.
- `HEAD` غير موجود في مستودع بلا commits.
- أمر فحص التعارضات نفسه فشل.

كلها تتحول في النهاية إلى:

```python
return "", untracked_files
```

ثم قد تظهر للمستخدم رسالة:

> لا توجد أي فروقات Git جديدة

وهذا يخالف مبدأ **Fail-Closed** ويجعل الخطأ التنفيذي غير قابل للتمييز عن غياب التغييرات.

### الإصلاح

- لا تستخدم fallback عند فراغ `stdout`؛ **الـ Diff الفارغ نتيجة صحيحة**.
- تحقق من `returncode` لكل أمر، بما فيها `ls-files -u`.
- تحقق من المرجع بـ`rev-parse --verify`.
- لا تنتقل تلقائياً إلى `HEAD~1`؛ فهذا يغير دلالة العملية دون علم المستخدم.
- لا تبتلع استثناء Merge Conflict ثم تعيد نتيجة فارغة.

## ثانياً: إدراج Untracked هو إدراج أسماء فقط، وليس إدراج الكود

الناتج الحالي يحتوي:

ولكنه لا يحتوي محتوى الملف. لذلك عبارة أن الملفات الجديدة أُدرجت «حتى لا تسقط من المراجعة» غير متحققة بالكامل؛ **اسم الملف يظهر، لكن الكود الجديد لا يصل إلى المراجعة**.

إما:

1. إضافة محتوى الملفات غير المتتبعة بعد تطبيق فحوص الاسم والحجم والثنائية والأسرار، أو
2. تغيير الرسالة صراحة إلى: «أسماء ملفات غير متتبعة، ومحتواها غير مدرج».

كما يجب تطبيق سقف الحجم على هذا الجزء أيضاً.

## أ. خلل خطير في الـ Fallback داخل Git Diff

هذا الشرط غير صحيح:

```python
if proc.returncode != 0 or not diff_out.strip():
```

**فراغ الـ Diff ليس فشلاً.** بل هو نتيجة صحيحة تعني عدم وجود اختلافات tracked.

عندما لا توجد تغييرات، ينتقل السكريبت إلى:

```python
git diff HEAD~1 -- .
```

وهذا قد يعرض **آخر Commit**، رغم أن المستخدم طلب تغييرات شجرة العمل الحالية. كذلك إذا كان هناك ملفات untracked فقط، يكون `diff_out` فارغاً، فيضيف السكريبت diff آخر Commit بلا مبرر، ثم يضيف أسماء الملفات غير المتتبعة.

كذلك قد يخفي الفشل الحقيقي:

- `git` غير موجود.
- المسار ليس مستودعاً.
- المرجع `--since` غير صالح.
- `HEAD` غير موجود في مستودع بلا commits.
- أمر فحص التعارضات نفسه فشل.

كلها تتحول في النهاية إلى:

```python
return "", untracked_files
```

ثم قد تظهر للمستخدم رسالة:

> لا توجد أي فروقات Git جديدة

وهذا يخالف مبدأ **Fail-Closed** ويجعل الخطأ التنفيذي غير قابل للتمييز عن غياب التغييرات.

### الإصلاح

- لا تستخدم fallback عند فراغ `stdout`؛ **الـ Diff الفارغ نتيجة صحيحة**.
- تحقق من `returncode` لكل أمر، بما فيها `ls-files -u`.
- تحقق من المرجع بـ`rev-parse --verify`.
- لا تنتقل تلقائياً إلى `HEAD~1`؛ فهذا يغير دلالة العملية دون علم المستخدم.
- لا تبتلع استثناء Merge Conflict ثم تعيد نتيجة فارغة.

# الحكم النهائي

**لم تُغلق الملاحظات السبع بنسبة 100%، ولا أمنح v4.0 الـ Production-Ready Sign-off في صورته الحالية.**

الإصدار أصلح معظم العيوب السابقة فعلاً، وأصبح **Release Candidate قوياً**، لكن بقي **خلل أمني في مسار Git، وخللان منطقيان مؤثران** تمنع الاعتماد النهائي.

## 1. مطابقة الصمامات السبعة

| البند | الحكم | الدليل المختصر |
|---|---|---|
| **1. دلالات Git وMerge Conflicts** | **جزئي، وليس 100%** | أُلغي fallback إلى `HEAD~1`، وفحص التعارضات يفشل بوضوح. لكن فشل أمر `ls-files --others` يُتجاهل، وقد تُطبع رسالة «شجرة العمل نظيفة» رغم وجود ملفات untracked مستبعدة. |
| **2. محتوى Untracked** | **مطبق وظيفياً، مع Fail-Open** | المحتوى يُقرأ ويُدرج فعلاً عبر `read_source_file_safely`. لكن الملفات المرفوضة أمنياً أو غير UTF-8 تختفي بصمت، ثم قد يعلن السكريبت أن الشجرة نظيفة. |
| **3. فحص أسرار Diff** | **مغلق في المسار الطبيعي** | `scan_text_for_secrets(diff_text)` يسبق `write_atomic` والنسخ، وعند الاشتباه يعود بـ`1`. لا يوجد مسار تصدير للـ Diff بعد اكتشاف النمط. |
| **4. مصفوفة الأسرار والمسارات** | **تحسن كبير، وليست ضماناً شاملاً** | المسار النسبي الكامل يُفحص، والمصفوفة أوسع. لكن لا يمكن إثبات خلو المحتوى من الأسرار بـRegex؛ تبقى الحاجة إلى `gitleaks` أو `detect-secrets` للاستخدام المؤسسي. |
| **5. Two-Pass Manifest** | **جزئي، غير مطابق 100% عند بلوغ السقف** | الشجرة والترويسة تُبنى من كل `accepted_files`. إذا أوقف `break` الحزم بسبب السقف، تظل الشجرة والترويسة تشملان ملفات لم تُحزم. |
| **6. التخزين خارج المشروع** | **مغلق في المسار الافتراضي** | `target_dir.parent / ...` صحيح. لكن عند تمرير `--out` داخل المشروع، رسالة «تم حفظ الحزمة خارج المشروع» تصبح غير صحيحة. |
| **7. Gitignore + Atomic/fsync + السقف** | **جزئي** | `git ls-files` و`fsync` و`os.replace` جيدة. لكن سقف الحمولة غير صارم، وDiff غير محدود، والكتابة قد تتم بعد تجاوز السقف. |

## 2. العيوب المانعة المتبقية

### أ. ثغرة أمنية: يمكن تجاوز Symlinks Guard في مسار Git

في:

```python
p = (target_dir / line.strip()).resolve()
```

الدالة `resolve()` تتبع الرابط الرمزي **قبل** الفحص اللاحق. بعد ذلك:

```python
file_path.is_symlink()
```

يفحص الهدف المحلول، لا مدخل الملف الأصلي. لذلك قد يتحول رابط داخل المشروع يشير إلى ملف خارجه إلى مسار عادي، ثم يجتاز الفحص ويُقرأ ويُصدَّر.

هذا يناقض صراحةً ادعاء منع تتبع الروابط، وهو **مانع أمني للـSign-off**.

**الإصلاح:** احتفظ بالمسار غير المحلّ أولاً، وارفض `lstat/is_symlink` قبل `resolve()`، وتحقق من احتواء المسار داخل الجذر دون اتباع الورقة. استخدم مخرجات Git بصيغة `-z` بدلاً من `splitlines()` و`strip()`.

### ب. رسالة «Working Tree Clean» قد تكون كاذبة

الشرط الحالي:

```python
if not diff_text.strip() and not untracked_items:
```

لا يثبت نظافة الشجرة؛ فقد توجد ملفات untracked لكنها استُبعدت بسبب:

- مسار حساس.
- حجم أكبر من 2MB.
- ملف ثنائي.
- فشل قراءة.
- اكتشاف سر.
- فشل أمر `ls-files --others` نفسه.

عندها يطبع السكريبت:

> شجرة العمل نظيفة تماماً

رغم وجود ملفات فعلية لم تُراجع. هذا **Fail-Open منطقياً** وقد يخفي تعديلات عن المراجعة.

يجب التفريق بين ثلاث نتائج: **نظيفة، تم التصدير، وتغييرات موجودة لكنها حُظرت أو تعذر فحصها**.

### ج. سقف الحمولة ما زال غير صارم

- وضع `--diff` لا يطبق `MAX_BUNDLE_BYTES` إطلاقاً.
- الحزمة الكاملة عند تجاوز السقف تطبع تحذيراً فقط، ثم:

```python
write_atomic(out_file, full_payload)
```

أي **تستمر في الكتابة رغم تجاوز السقف**.
- ميزانية 12MB داخل الحزم لا تشمل الـPrompt النهائي بدقة.
- لا يوجد سقف مقابل لـDiff والملفات غير المتتبعة قبل تجميعها في الذاكرة.

إذن بند «سقف الحمولة الإجمالية الصارم» **غير مغلق**.

### د. البيانات الوصفية تفسد عند بلوغ السقف

الشجرة والترويسة تُبنيان من جميع `accepted_files`، ثم قد تتوقف الحلقة عند السقف. النتيجة:

- الشجرة تسرد ملفات غير موجودة في الحمولة.
- `Verified Files Count` أكبر من `packed_count`.
- الترويسة لا تعكس الملفات المحزومة فعلياً.

إذن عادت مشكلة عدم تطابق البيانات الوصفية عند بلوغ السقف، رغم نجاح Two-Pass في الحالة غير المبتورة.

### هـ. ملاحظات أقل حدة

- رسالة «تم حفظ الحزمة خارج المشروع» قد تكون غير صحيحة إذا مرر المستخدم `--out` داخله.
- وضع `--diff` لا يطبق `MAX_BUNDLE_BYTES` قبل بناء الحمولة أو كتابتها.
- ملف الإخراج الافتراضي خارج المشروع جيد، لكن عند `--out` داخل المشروع تبقى رسالة «خارج المشروع» غير دقيقة.
- ادعاء منع Race Condition بالكامل غير صحيح؛ الفحص عبر المسار ثم `open()` لا يلغي كل سباقات تبديل الملف، رغم أن القراءة ذاتها أصبحت موحدة.

5. ✅ هل حدّثت سجل الذاكرة؟ نعم، تم التوثيق تحت القرار #181 في `CHANGELOG_DECISIONS.md`.

### 1️⃣ لو بتسأل: "هو الحل / العرض ده بقاله كتير؟" ⏳

* **السكريبت الصيني اللي ظاهر عندك تحت يمين (`注入已挂载 12个月`):**
  - ده سكريبت Tampermonkey / أداة منتشرة على منتديات المطورين الصينية (زي Linux.do و V2EX) للحصول على الـ 12 شهر مجاناً أو الالتفاف على باقة الـ AI Premium، **وجوجل قفلت معظم ثغرات الـ Backend الخاصة بيه مؤخراً**، وده بالضبط سبب إنه معلق!

### 2️⃣ ليه اللودينج (الدايرة الزرقا) معلقة ومش راضية تفتح؟ 🔄
السبب المعماري لتعليق الصفحة في حلقة مفرغة:
1. **السكريبت الصيني عامل Hooking:** السكريبت بيعترض طلبات الـ API الخاصة بجوجل (`batchexecute` أو `GoogleOneUi`) وبيحاول يعدل الـ Payload، وجوجل بترد بـ `400 Bad Request` أو `CORS Error` فالمتصفح بيفضل مستني استجابة مش هتيجي.
2. **لخبطة الحسابات (`/u/5/`):** أنت فاتح الحساب رقم 5 في نفس البروفايل، وخدمات الدفع بـ Google Pay دايماً بتضرب لما ميكنش الحساب هو الأساسي (`/u/0/`).
3. **عدم تطابق الـ IP والدولة:** يوتيوب بريميوم لايت مش متاح في كل الدول، ولازم الـ IP يطابق ريجن الحساب بالمللي.

### 3️⃣ الحل العملي عشان تفك التعليقة دي وتكمل: 🛠️

1. **عطّل السكريبت مؤقتاً:**
   - اقفل سكريبت Tampermonkey / الإضافة الصينية مؤقتاً واعمل `Ctrl + F5`، وشوف هل الكارتين هيفتحوا معاك طبيعي ولا لأ.
2. **افتح في متصفح خفي (Incognito):**
   - افتح نافذة جديدة كلياً `Ctrl + Shift + N`.
   - سجّل دخول بالإيميل ده **لوحده** بحيث يكون هو الحساب الرئيسي (`/u/0/`).
3. **شغّل VPN على نفس دولة الحساب (مثلاً أمريكا لو بالدولار):**
   - اتأكد إن الـ IP نضيف ومش مصنف Datacenter.
4. **لو عايز تفحص الخطأ بالضبط:**
   - اضغط `F12` وادخل على تبويب **Network** واعمل Refresh، هتلاقي في طلب باللون الأحمر (فاشل) هو اللي معلق اللودينج، تقدر تشوف الـ Response بتاعه إيه سببه (غالباً `Blocked by Client` أو `Invalid Account Context`).

## 2. إيه الفرق بين `commit` و`push` و`PR` و`merge`؟

| العملية | معناها |
|---|---|
| **Save** | حفظ التعديل في ملف داخل الـSandbox فقط |
| **Commit** | تسجيل نسخة من التغييرات في Git المحلي؛ لسه ممكن تضيع مع فقد بيئة العمل |
| **Push** | إرسال الـcommits إلى GitHub؛ هنا الشغل بقى محفوظًا خارج الـSandbox |
| **PR — Pull Request** | فتح طلب لعرض الفرق بين فرع العمل و`main` ومراجعته |
| **Merge** | إدخال تغييرات فرع العمل إلى `main` |

**الـPR نفسه لا يرفع الملفات ولا يدمجها.** الملفات بتكون مرفوعة بالفعل بالـpush، والـPR يعرضها للمراجعة والدمج.

وفي الاستخدام المعتاد، **كل push جديد لنفس فرع الـPR المفتوح يظهر فيه تلقائيًا**؛ مش بنفتح PR جديد لكل ملف.

### مثالنا الحالي

```text
GitHub
├── main
│   └── النسخة الأساسية الحالية
│
└── genspark_ai_developer
    └── التشخيص والخطة وسجل الاستئناف المرفوعون
            │
            └── PR #5 يعرض الفرق لدمجه لاحقًا
```

**يعني الخطة مش منتظرة الدمج علشان تكون محفوظة. هي محفوظة على GitHub بالفعل.** بس علشان تشوفها، افتح فرع العمل أو رابط الملف اللي بعته، بدل ما تتصفح `main` فقط.

```text
الوكيل يعدّل
    ↓
يرفع إلى فرع العمل
    ↓
PR
    ↓
الاختبارات المطلوبة تنجح
    ↓
Auto-merge إلى main
```

يمكن إعداد ذلك إذا كانت إعدادات المستودع والصلاحيات والقواعد تسمح. ولو فيه مراجعة بشرية إلزامية، الدمج ينتظر تحققها.

### الاختيار الثالث: الرفع المباشر إلى `main`

**Git نفسه يسمح بده تقنيًا** إذا الصلاحيات وقواعد المستودع تسمح:

```text
تعديل → commit → push إلى main
```

ولا يحتاج PR من ناحية Git ذاتها.

لكن:
- قد تدخل نسخة ناقصة أو غير مختبرة مباشرة.
- قد يحدث تعارض مع شغل شخص أو وكيل آخر.
- قد يبدأ نشر تلقائي.
- **في بيئة الوكيل الحالية، التعليمات الملزمة بالفرع والـPR لا تسمح لي باستبدالها برفع مباشر.** أي وكيل آخر لازم يتحقق من تعليماته وصلاحياته أيضًا.

**يعني الخطة مش منتظرة الدمج علشان تكون محفوظة. هي محفوظة على GitHub بالفعل.** بس علشان تشوفها، افتح فرع العمل أو رابط الملف اللي بعته، بدل ما تتصفح `main` فقط.

---

## 3. ليه ما رفعتش على `main` مباشرة؟

### أولًا: تعليمات بيئة العمل الحالية

أنا في الجلسة دي عندي تعليمات ملزمة باستخدام فرع:

```text
genspark_ai_developer
```

ورفع التغييرات مع PR. **ده سبب مباشر لطريقة شغلي هنا، مش قرار GitHub لوحده.**

### ثانيًا: فصل الحفظ عن اعتماد التغيير

أحيانًا بنحتاج نحفظ:
- خطة لسه ما وافقتش عليها.
- تشخيص لسه بيتراجع.
- جزء إصلاح لم تكتمل أجزاؤه المرتبطة.
- اختبارات تكشف المشكلة ولسه الإصلاح ما اكتملش.

نرفع ده على فرع العمل علشان ما يضيعش، **من غير ما نجعله النسخة الأساسية للمشروع**.

ولو `main` مرتبط بنشر تلقائي، دخوله هناك ممكن يشغّل نشرًا أيضًا؛ ده يعتمد على إعدادات المشروع.

### ثالثًا: حماية الفروع — لو كانت مفعّلة

GitHub يسمح بوضع قواعد تمنع الرفع المباشر أو تشترط اختبارات ومراجعات.

لكن أصحح نقطة في الكلام اللي كتبته: **مش كل المستودعات ولا بالضرورة معظمها عندها الحماية دي مفعّلة، وأنا لم أتحقق هنا من قواعد حماية `main` في مستودعك.** فلا أقول إن GitHub أجبرنا عليها في حالتك.

---

## 4. هل ممكن التحديث يبقى تلقائي من غير ما تطلب مني كل مرة؟

**نعم. عندك 3 مستويات مختلفة:**

### الاختيار الأول: رفع تلقائي لفرع العمل — أنسب حل للحفظ

تديني سياسة ثابتة:

> بعد كل جزء صغير، احفظ وارفع بنفسك، ولا تنتظر مني طلب push.

ساعتها الوكيل ينفّذ:

```text
تعديل → فحص مناسب → commit → push → تحديث سجل الاستئناف
```

**الميزة:** شغلك محفوظ باستمرار، و`main` يظل منفصلًا عن الأجزاء غير المعتمدة.

**القيد:** ده تلقائي ضمن تنفيذ الوكيل، مش مراقبة مستقلة مستمرة. لو الجلسة توقفت قبل الـpush، الجزء الأخير غير المرفوع قد يضيع.

### الاختيار الثاني: رفع تلقائي + دمج تلقائي بعد نجاح الاختبارات

ده يحقق رغبتك إن **`main` يتحدث من غير موافقة يدوية في كل مرة**، مع الاحتفاظ بالـPR:

```text
الوكيل يعدّل
    ↓
يرفع إلى فرع العمل
    ↓
PR
    ↓
الاختبارات المطلوبة تنجح
    ↓
Auto-merge إلى main
```

يمكن إعداد ذلك إذا كانت إعدادات المستودع والصلاحيات والقواعد تسمح. ولو فيه مراجعة بشرية إلزامية، الدمج ينتظر تحققها.

**ده حل مناسب لو هدفك: «حدّث main تلقائيًا، بس بعد التأكد إن التغيير اجتاز الشروط».** وليس بعد كل حفظ جزئي.

### الاختيار الثالث: الرفع المباشر إلى `main`

**Git نفسه يسمح بده تقنيًا** إذا الصلاحيات وقواعد المستودع تسمح:

```text
تعديل → commit → push إلى main
```

ولا يحتاج PR من ناحية Git ذاتها.

لكن:
- قد تدخل نسخة ناقصة أو غير مختبرة مباشرة.
- قد يحدث تعارض مع شغل شخص أو وكيل آخر.
- قد يبدأ نشر تلقائي.
- **في بيئة الوكيل الحالية، التعليمات الملزمة بالفرع والـPR لا تسمح لي باستبدالها برفع مباشر.** أي وكيل آخر لازم يتحقق من تعليماته وصلاحياته أيضًا.

---

## 5. طيب «أول ما الملف يتغير، يترفع فورًا» حرفيًا؟

ده يحتاج **File Watcher**: برنامج يراقب مجلد المشروع، وبعد تغيّر الملفات يشغّل الحفظ والرفع.

لكن ما أنصحش بمراقب يرفع كل شيء بلا تمييز؛ لأنه ممكن يرفع:
- ملفًا لسه بيتكتب.
- تعديلًا قبل اكتمال الملفات المرتبطة به.
- أسرارًا أو logs أو ملفات runtime.
- آلاف التغييرات المؤقتة.

النسخة الآمنة منه تحتاج:
- قائمة ملفات ومجلدات مسموح رفعها.
- استبعاد الأسرار والملفات المؤقتة.
- انتظارًا قصيرًا بعد آخر تغيير لتجميع التعديلات.
- منع تزامن عمليتي Git.
- معالجة فشل الشبكة والتعارضات.
- الرفع إلى **فرع checkpoints**، وليس دمج كل حفظ جزئي في `main`.

**والمراقب الموجود داخل Sandbox نفسه يتوقف مع الـreset**؛ يحتاج تشغيله مجددًا بعد الاستعادة. كذلك GitHub Actions وحدها لا تستطيع التقاط ملفات محلية لم تُرفع بعد.

---

## 6. البرومبت الجاهز لأي وكيل

ده برومبت أنصحك تستخدمه أول جلسة، أو مع مشروع جديد:

```text
اعتمد سياسة حفظ واستئناف مستمرة لهذه المهمة، ضمن نطاق العمل الذي وافقت عليه:

1. قبل العمل افحص حالة المستودع، الفرع الحالي، آخر remote commit،
   وتعليمات المشروع. لا تفترض أن الحالة المحلية هي الأحدث.

2. استخدم فرع عمل ثابتًا ومعلنًا، وافتح أو حدّث PR إلى main.
   لا تنتظر مني طلب commit أو push بعد كل خطوة.

3. قسّم الشغل إلى أجزاء صغيرة. بعد كل جزء:
   - نفّذ الفحص المناسب.
   - سجّل التغييرات في commit واضح.
   - ارفعها إلى GitHub قبل الانتقال إلى الجزء التالي.
   - تأكد من نجاح الرفع، ولا تعتبر commit محليًا حفظًا بعيدًا.

4. احفظ سجل الاستئناف في genspark/recovery_state.json:
   - المهمة والنطاق المعتمد.
   - ما تم وما لم يتم.
   - الملفات التي تغيّرت.
   - نتائج الاختبارات الفعلية.
   - آخر checkpoint مدفوع والخطوة التالية.
   لا تحفظ أسرارًا أو محتويات حساسة من الملفات التي قرأتها.

5. ارفع فقط الملفات المصرح بها. لا تستخدم git add . بلا مراجعة،
   ولا ترفع tokens أو cookies أو حسابات أو ملفات runtime أو logs حساسة.

6. إذا كان checkpoint وسيطًا أو غير مكتمل، وضّح ذلك في السجل والـPR.
   لا تعلن أنه صالح للتشغيل أو تدمجه قبل اجتياز شروط القبول.

7. بعد أي reset أو جلسة جديدة، استعد آخر checkpoint من GitHub
   وافحص حالته قبل التنفيذ؛ لا تكرر الأجزاء المحفوظة.

8. لو فشل push أو ظهر تعارض، لا تدّعِ أن العمل محفوظ.
   عالج المشكلة بأمان أو أخبرني بالعائق، ولا تحذف عمل الآخرين.

9. سياسة الحفظ هذه لا تعني تفويضًا بميزات جديدة أو نشر أو دمج.
   لا تدمج في main إلا وفق تفويض الدمج المعتمد وقواعد المستودع.

10. في نهاية كل مرحلة، أعطني الفرع ورابط PR وآخر commit مدفوع
    وحالة الملفات المحلية والخطوة التالية.

إذا تعارضت هذه السياسة مع تعليمات بيئتك أو صلاحيات المستودع،
اشرح التعارض قبل تنفيذ مسار مختلف.
```

ولو أردت **دمجًا تلقائيًا أيضًا**، تضيف بعد الاتفاق على الاختبارات والنطاق:

> أفوّض الدمج التلقائي للتغييرات الواقعة داخل النطاق المعتمد فقط، بعد اجتياز الاختبارات المطلوبة وقواعد المستودع، بشرط أن تسمح تعليمات بيئتك بذلك. هذا لا يجيز تجاوز حماية الفروع أو دمج checkpoints ناقصة.

## الخلاصة لحالتك

**إنت لا تحتاج الرفع المباشر على `main` علشان تحمي الشغل من الـresets. تحتاج push مستمر ومؤكد إلى GitHub.**

وأفضل فصل هو:

- **الحفظ:** تلقائي على فرع العمل بعد كل جزء صغير.
- **تحديث `main`:** بعد اكتمال التغيير واجتياز الاختبارات، يدويًا أو تلقائيًا بتفويض واضح.
- **الاستعادة:** من فرع العمل وسجل `genspark/`، مش من `main` وحده.

وملاحظة أمنية: التوكن الذي شاركته سابقًا يُفضّل إلغاؤه واستبداله بوسيلة وصول محدودة الصلاحيات تُضبط عبر إعدادات الأسرار، بدل تكراره داخل المحادثات.

#### 1. ليه هو فهمك بالظبط؟
- **لقط جوهر قلقك:** هو فهم إن هدفك الأساسي مش مجرد "عناد في استخدام `main`"، بل إنك **خايف شغلك يضيع** لو الجلسة فصلت أو الـ Sandbox اتمسح، وعايز الـ GitHub يكون مراية حية لكل خطوة بتتعمل بدون ما تضطر تقول "ارفع" كل دقيقة.

#### 2. نقاط القوة في رده:
- **تحذيره من الـ File Watcher العشوائي:** ده تحذير في مكانه تماماً؛ لأن لو فيه أداة بترفع تلقائياً مع كل حرف بيتكتب، هترفع ملفات نصها بايظ، أو هترفع ملفات حساسة وتوكنات بالخطأ.
- **البرومبت اللي كتبهولك (النقطة 6):** ده برومبت **ممتاز واحترافي جداً**، بيجبر أي وكيل يشتغل بسياسة الـ Checkpoints (حفظ ورفع كل خطوة ناجحة في صمت وبدون ما يعطلك).

#### 📌 الخلاصة:
الوكيل فهمك تماماً، والحل اللي طرحه هو **أفضل ممارسة (Best Practice)** تجمع بين:
1. **راحة بالك:** الشغل بيترفع أوتوماتيك أول بأول بدون ما تطلب.
2. **الأمان:** `main` يفضل نضيف وشغال، وشغلك محفوظ في فرعك الخاص ومعمول له سجل استرجاع (`recovery_state.json`).

2. **الخوف من ضياع الشغل:** لو جلسة الوكيل فصلت فجأة أو الـ Sandbox بتاعه اتمسح، إزاي توصل للشغل وتدمجه من غيره؟
3. **لبس بخصوص مكان الملفات:** هل الملفات محبوسة جوه الـ PR ومش موجودة على الفرع، ولو مقدرتش تعمل Merge الشغل هيضيع؟

يا غالي **اطمن بنسبة 1000%، مفيش سطر كود واحد هيضيع**، وتعالى أفهمك كل نقطة ببساطة:

---

#### 🛑 أولاً: ليه الزرار مقفول عندك ومكتوب `failing merge requirements`؟
الرسالة دي طالعة من **GitHub نفسه مش من الوكيل**، وبتظهر لسبب من التلاتة دول (هتلاقيه مكتوب في صندوق فوق أو تحت الزرار ده مباشرة):
1. **فيه فحص آلي ساقط (Failing Check):** المستودع عليه GitHub Action أو اختبارات أوتوماتيكية طلعت علامة `❌` حمراء، وجيت هاب بيمنع الدمج لحد ما الاختبار يعدي.
2. **محتاج مراجعة (Review Required):** إعدادات المستودع بتشترط موافقة مراجع (Approve) قبل الدمج.
3. **الـ PR معمول Draft:** متسجل كمسودة ولسه متحولش لـ `Ready for review`.

> 💡 **هل لازم الوكيل يعمل حاجة؟**
> لو السبب كود سقط في الاختبارات، أيوة هو لازم يصلحه. أما لو السبب إعدادات حماية في المستودع (Rules) فدي إنت صاحب المستودع وتقدر تعدلها من إعدادات GitHub (Settings -> Branches).
